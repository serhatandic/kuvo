# Also Apply from another computer

Proposed, unimplemented design for Work Queue #668, finding 12. “Also Apply to…” takes settings changes already made on one computer and applies them to each selected computer. The destination box owns the preview, installation and recovery. A client picks computers, shows the box’s preview and collects confirmation. Each destination has its own result.

## Current behavior

[`POST kuvo/config/apply`](../box/src/link/areas/apply.ts) translates a list of changes against the destination’s settings. It preserves the destination’s shell, absolute worktrees directory and unrelated permission entries. It reports missing parent entries and Mac-only servers separately. Its dry run returns the key names the changed settings refer to. The retired phone client handled netting, key copying, retries and cleanup itself. On the desktop, “Also Apply to…” needs its own screen work. New-computer seeding and account sign-ins are separate work.

## Request and preview

Add `config.apply.from` to the per-computer feature list. Keep the existing `config.apply` shape for old clients. The new flow has three calls:

| Call to the destination box | Result |
| --- | --- |
| `POST kuvo/config/apply` with `{from: {computer, changeSet}, dry: true}` | The destination resolves the source’s saved batch and runs the existing translation. It returns a short-lived plan ID, source and destination names, redacted changes, kept and skipped entries, and which supported integration keys would be brought or reused. Nothing is written to settings or the key store. |
| `POST kuvo/config/apply` with `{plan, approval}` | The destination validates the exact preview confirmed by the user. It records a durable operation under the plan ID and may return `202` while it finishes. Repeating that confirmation retrieves the same operation. |
| `GET kuvo/config/apply/<plan>` | The originator reads the result after a reconnect or timeout. Results distinguish applied, already set, needs a fresh preview, unavailable, and recovery pending. An applied result carries the destination’s config revision so clients can refresh through the existing settings route. |

The source records opaque receipts for eligible, successful Settings edits, including any supported catalog additions. It computes the net batch from those receipts in source order. For each repeated path, one selected receipt’s after must equal the next selected receipt’s before. A gap refuses the batch so an intervening edit cannot be included by coalescing. For a continuous chain, keep the first before and final after, drop no-ops, and reject ambiguous overlapping paths. Receipts expire and are scoped to the authenticated editor and source box. `changeSet` names that exact batch. The destination accepts that ID and the source’s stable computer ID in the current setup. Request URLs, credential names and change values come from box-owned records. Each peer request uses the membership directory for addressing.

The destination uses one translation for preview and commit. It binds a plan to the authenticated client, source batch and members, setup epoch, destination revisions and key dispositions, approved key transfers and expiry. It rechecks all of them before applying. If a referenced setting, catalog policy or credential changes, the answer requests a fresh preview. Catalog additions are planned alongside their dependent edits before anything is installed. Supported additions resolve through the destination’s catalog. Dependencies that cannot be installed on that destination are marked together. Unsupported entries appear in the preview with a reason. A confirmation covers the exact remaining changes. Editing the selection produces a new plan.

## Peer and credential authorization

Use authenticated and encrypted box-to-box transport with the current setup membership and peer keys. Both boxes check the setup and epoch, sender and receiver, and current membership at preview and commit. Batch export, including a settings-only preview, requires the source to verify the original editor’s authority. A source-issued delegation, obtained over an authorized source session, binds the editor and initiating client to the batch, destination and expiry. The destination presents it in the authenticated peer request. The source checks current access before releasing any batch metadata or values. A box that cannot identify the caller and enforce that authority refuses the flow. Key export requires an additional source-side grant. The source authorizes the exact batch and each eligible credential for this destination and operation after user confirmation. An export grant expires, is recipient-bound and signed by the source, and permits a retry only for the same operation. Preview uses metadata only. The trusted confirmation and proof the source accepts are security-review deliverables. Until an implementation has that proof, credential transfer stays disabled.

Resolve an exact structured reference to a reviewed catalog or provider credential slot. A string containing `KUVO_KEY_` does not qualify. Verify provenance, the intended service and endpoint, and the credential slot on both boxes. Existing destination keys for the same verified slot stay in place. An ambiguous slot, destination binding mismatch, unavailable key host, or missing or unapproved source key leaves the dependent changes blocked and identified in the preview. Only explicitly approved static integration or provider API keys are candidates. OAuth, refresh tokens, cookies, SSH keys, per-bot keys, vault items, and sign-in state remain outside this protocol. A dedicated peer message carries each approved transfer. Authorized legacy clients can still read values through `kuvo/keys/<name>`. The new grant governs this flow. Security review must decide when that compatibility surface can retire. Values travel from the source key store to the destination key store over the encrypted peer link and stay out of client responses, operation journals, audit records and logs. Audit records contain operation IDs and authorized actors, decision and result.

The current translator also accepts changes that can run code or change tool permissions. This peer operation starts with a reviewed allowlist of settings and schema shapes. Changes to commands, executable MCP definitions, endpoints or permission rules require separate review of what is eligible and how the actor approves the exact effect. An unsupported shape stays blocked even if the legacy local endpoint would accept it.

## Commit and recovery

The destination reserves a durable operation record before beginning. It persists plan bindings, per-setting preimages and intended postimages, per-key intent and opaque generation/ownership metadata. Values in this record use structured key references or redaction. Current requests share resident dispatch across HTTP, relay and SSH. Coordinate with retained standalone CLI, legacy settings and key writers, and Keychain mirror refresh. When both locks are needed, acquire the key-file lock before the config lock, following the existing key writer. A process-local key queue alone cannot enforce this. Fetch approved values outside the config lock. Revalidate the relevant state before installing keys and writing settings. Reuse the existing config writer and refresh path for the engine.

1. Stage incoming keys as operation-owned entries in the destination key store. Publish a key only if its destination slot is still vacant. Before config is visible, durably record each key installation. Verify that the authoritative key store and the engine-facing key file, when used, are both ready for the approved generation. Until then the entry remains staged. Backends need conditional create and conditional delete by generation or equivalent ownership, including the Mac host Keychain adapter. A backend without those operations cannot receive keys through this flow.
2. Commit the translated settings in one atomic config write, only against the approved destination revisions. The staged file carries a unique operation generation on the file itself, such as an extended attribute set before fsync and rename. The journal records the expected generation and resolved target before rename. Sync the target directory after rename. All participating config writers finalize a pending operation before replacing that file. A backend without a durable generation attached to the atomic write cannot take part. File, catalog and key effects participating in the write must be covered by the same recoverable operation. When catalog installation cannot be recovered this way, that entry stays blocked. Record final config revision and result before replying. An engine refresh that is temporarily unavailable is a separate retry after the settings have been saved.
3. At restart reconcile the journal against the recorded write and current state. A valid committed generation or saved final result identifies this operation’s write, even if a later edit has the same values. Finalize it and keep referenced keys. If the recorded pre-write generation still stands and the operation never published config, remove only keys installed by this operation that still have their recorded generation and are unused by surviving settings. If a config rollback is required, restore only the operation’s paths that still have its recorded postimage and revision. A later user edit or key replacement always wins. If ownership or commit state is ambiguous, report recovery pending and retain the entries until reconciled. After a lost reply, read the durable outcome using the same operation ID.

An unavailable peer during preview gives no plan. A disconnect during commit can be retried through the operation ID while the authorization is still valid. A removed peer, changed setup or expired authorization blocks further transfer. The destination can still complete local recovery. Use the same behavior for all clients. If either box lacks `config.apply.from`, the new flow reports that computer as unsupported. An old client can still call the existing local endpoint. The new flow surfaces its own failure to the client. For multiple destinations the client shows independent outcomes and retries only the affected destination.

## Before implementation

- Review peer membership and revocation checks, trusted confirmation, source export authorization, catalog eligibility and the key-store ownership primitives. Test replay, request substitution, another setup, a removed member, a changed batch, batch ID replay by another authenticated client, wrong endpoint or slot, and a malicious or malformed peer response. Verify that captured request traces and journals expose no credential values.
- Test no-op and partial previews, retained destination settings, missing parents, Mac-only servers, mixed-version peers, missing destination or source keys, local concurrent edits and recovery at each write boundary. Crash after config commit and before the reply must return the original result. A replaced key must survive recovery. Cover a crash between the Keychain write and creation of its engine-facing file, resident dispatch concurrent with retained CLI writers, and an unrelated editor setting the same value. Exercise Linux key files and the Mac Keychain adapter independently.
- Have the desktop screen owner design the destination preview, confirmation for named key transfers, and per-computer outcomes. Check the text and states with that owner before wiring the API.
