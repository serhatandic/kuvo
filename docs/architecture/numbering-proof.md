# Work Queue numbers across main-computer changes

Within a ranked setup running the quorum allocator, two distinct grants cannot authorize the same number, even across competing accepted leadership histories. A computer can spend the unspent part of its own durable grants while offline. When it runs out, creation succeeds with a stable item ID and the item waits for a number. An assigned number stays with its item even if the leadership history that granted it later loses.

## Why the ranges are disjoint

1. **Common electorate.** The checkpoint that activates ranked succession establishes the numbering electorate. Subsequent certificates carry that same set of computer keys. A certificate is checked against the preceding electorate when the box knows it. The electorate is separate from the current routing roster. When a computer leaves the roster it stops voting, and its departure cannot lower the majority threshold or change the intersection between competing quorums. An existing ranked history can derive the electorate from its verified activation checkpoint. A computer with neither that history nor a certificate carrying the electorate waits. [Electorate and checkpoints](../../box/src/link/setup/checkpoint.ts) · [Certificate validation](../../box/src/link/setup/leadership.ts)
2. **A vote reserves space durably.** A proposal identifies its setup, epoch, exact leadership certificate, nonce and inclusive range. Only the primary of that position proposes it. A voter checks that position against its locally accepted certificate and checks the authenticated sender. It accepts a new proposal only if its first number is above the voter's durable high-water mark and the local ledger and legacy ceiling it knows. It records the upper end of the entire range before sending a vote. A retry of the exact last proposal can receive the same vote. The vote lives in the computer's local number ledger, outside the shared checkpoint that branch reconciliation can replace. A losing or abandoned proposal may therefore leave a gap. [Vote checks](../../box/src/link/work-queue/number-quorum.ts) · [Persistence and mail](../../box/src/link/work-queue/numbers.ts)
3. **A majority before issuance.** The primary counts one authenticated reply per eligible voter for the exact proposal. It persists the resulting grant before answering the requester. The grant binds the range to one computer and one ask ID. If two proposals get majorities, their voter sets share at least one key. That voter accepted one range before the other, and the second started above the end of the first. This applies to the whole reservation, including unused numbers and fresh import claims. A later primary starts from what it knows and retries above the floors reported by voters. A voter that has accepted a later epoch cannot endorse fresh issuance under an earlier epoch. Voters on a competing tip also reject proposals for the former tip. Delayed replies can only complete a range already set aside by a majority. [Proposal, retry and grant replay](../../box/src/link/work-queue/numbers.ts)
4. **A number is consumed once.** A computer saves its grant against the outstanding ask, then durably consumes each number before attaching it to an item. The queue persists a new assignment before publishing it. Pending ownership transfers hold numbering at the source so a carried item cannot get different numbers from both computers. New ranked imports can claim previously unallocated numbers through the same quorum. An import retry keeps a number already shown on the item. Setup merges reserve the destination range through the same allocator and retain source-namespace references as aliases. ## Waiting and compatibility

A client sees `numberPending: true` on ordinary items awaiting allocation, with no `number` field. Source-backed items already identified by a source reference do not enter that state. The item remains readable and editable by its stable ID. A `#N` lookup only matches an item with an assigned number or an existing historical alias in the relevant namespace. Background number rounds request new blocks and fill waiting items automatically.

The guarantee assumes the participating issuers run the quorum allocator and voter keys retain their durable state. Previously exclusive blocks remain valid. The allocator cannot recover reservations already lost by competing histories on older versions. Upgraded ranked standbys refuse the old ordinary allocation save, and upgraded ranked recipients require the quorum grant path. Two old computers running an old primary and standby can still issue under the old rules. Setup-free and non-ranked setups retain their previous allocation paths. The designated-standby path continues to provide disjoint allocation within its one accepted succession history.

Electorate reconfiguration is not implemented. If fewer than a majority of the original voters remain in the setup, new numbers wait even if a majority of the current roster is available. Losing or rolling back the durable disk of a voter while reusing its key is outside the proof. A merge reserves its destination range from the source snapshot's high-water mark. Source snapshots include the local vote and observed floors, but source sealing does not yet collect reservations hidden on a competing history. A source item above the snapshot's ceiling causes settlement to stop.

## Checks

The one-ledger tests cover recipient-bound replay, the inherited floor, exhaustion, lease loss and withholding a grant until durable standby acceptance. The ranked test uses signed competing takeovers, independent voter disks and authenticated peer mail. Both successors initially propose the same range and both wait. After one majority allocates, a later branch retries above a shared voter's durable floor, and that branch allocates a different number while the losing branch's item keeps the number it showed. The offline test covers the last locally granted number, creation and editing by ID during exhaustion, and the absence of a numeric match before assignment.
