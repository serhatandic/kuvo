# Attachment inventory for backup and removal

This closes priority 1 of the audit at `e4e56a9b7:docs/architecture/audit-f126eb531.md`, based on local main at `f126eb531`.

- The session attachment store owns the regular files under the Box and Mac attachment roots. A leaf name has no backup semantics. The Box's per-message slots, older flat session files, and Mac composer files keep their existing addresses. Capture still honors session ownership fences. Expiry and deletion remain the session store's responsibility.
- A Work Queue item's explicit file list defines the promised paths and, when recorded, the byte counts. Capture reads the lists and copies the payloads under the queue writer lock. A missing directory, absent or non-regular listed leaf, or size mismatch fails capture. Explicit lists exclude unlisted leftovers from interrupted writes. Older items without a list retain the ordinary durable file walk. An undoable item still owns its listed files. For readiness checks, the lock covers the inventory and queue records. The payload digests are computed after release to keep large files from extending the writer lock.
- Storage declarations select SQLite snapshots only for the engine and Insights database stores. Attachment files are opaque bytes regardless of name or contents. Wipe readiness excludes the same telemetry and volatile counters as before and still covers the wider bot working folders and explicitly selected projects.
- Restore stages files at logical addresses, upgrades the layout, and then reads the same inventory. Legacy archives still restore the available bytes and report missing or short queue payloads. A soft-deleted item keeps its undo files whenever current ownership and deletion evidence allow it. Local conflicts and ownership fences still govern placement.
- Wipe readiness binds the current names and bytes. For a requested export the hashes of the bytes fed to encryption must match that selected inventory, including the set of attachment paths. The download and authentication step separately checks that the destination durably kept the point. Readiness is checked again before erasure. An incomplete export stops in review without a wipe grant. Existing cancellation or explicit revision records the user's next choice.
- The readiness hash has a new domain and cannot reuse a point selected under the earlier rules. A ready export carries the inventory version in removal-only progress. An updated primary records it before issuing a grant and withdraws unversioned grants instead of resending them. The withdrawn generation remains valid for a late authenticated completion of the same operation. Cancellation and revision remain closed because the earlier grant may have reached the source. The encrypted container and saved attachment format remain compatible.

## Verification boundary

The closure fixtures use normal Box session-send and Work Queue create routes, an enrolled replacement with no prior user payloads, and a disposable disk destination. They compare binary bytes after source wipe and restore, including temporary-looking names, dotfiles, an empty file, and non-SQLite `.db` data. Another fixture removes a listed payload and checks the pending error, retained data, refused bypass and explicit cancellation. Two fixtures withhold a wipe grant, then add a session upload or rewrite a same-length attachment before releasing it. The source invalidates the grant and retains the new bytes.

Additional disposable cases check a stale attachment digest, a truncated queue file, old archive omissions, preserved undo bytes, authenticated pre-fix progress, registered grant withdrawal and late completion. These test inventory separately from archive authentication.

Session history has no independent manifest of expired or already missing files. Its inventory covers the regular payloads still managed by the attachment stores. A transcript can contain an absolute path from the old computer even when the bytes are recovered at the replacement's attachment root. An old source with a grant already delivered before upgrade can finish using the old rules. The mixed-version test exercises the authenticated progress shape with fixtures. Native client screens, live machines, and the separate automatic Relay backup/removal issue are outside these tests.
