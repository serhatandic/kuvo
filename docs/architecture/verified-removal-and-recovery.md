# Verified removal and recovery

Package 7 of `15fe20141:docs/architecture/audit-4b715e867.md`, based on `03de9f973`.

## Removal ownership

The current primary can commit revocation from a paired client through a member while the source is offline. The receiving Box applies revocation to ordinary Relay list, download, deposit and erase. The returning source can exchange operation-scoped removal mail. A plain wipe of a source with automatic Relay backups enters `choose-export`. The persisted refusal also applies to delayed instructions after the backup setting changes. Authorizing a disk or SSH export on the primary's local app preserves the revocation and resumes the same removal. The paired client can observe progress and the committed receipt.

The source binds prepared work to the setup, source identity, removal operation, accepted export choice and source generation. A stopped writer can still flush new data. The wipe worker rechecks the source after shutdown and authenticates the exact archive from its target before the erase commit. The source backup lock serializes this readback and commit with source-side explicit erase. For a configured pre-wipe backup the worker journals the exact point and reads it back after stopping writers and on a retry. For a prepared removal the current source inventory must still agree with the verified generation. A lost destination or changed generation leaves source bytes in place. A live removal-only worker can receive the retry after the normal keeper stops. If that listener disappears before the erase commit, restart the source's existing installation via its keeper (Kuvo Helper on a current own-home Mac), so the resident can resume removal delivery. Restarting the old app applies only to the app-owned 0.7 installation in the historical fixture. Once the durable journal enters the erasing phase, a restart finishes detaching and erasing the approved inode and reports completion from the receipt outside the old installation.

Automatic disk configuration requires a separate filesystem, and the configured filesystem identity is checked before readback. A revoked Relay source requires a separate filesystem or an SSH export to an enrolled computer. The source keeps that requirement across revisions and changes to the local schedule. Other explicit one-time exports can use a folder outside the source's erase boundary on the same volume, which survives the Kuvo wipe and shares the volume's physical failure risk. The device check distinguishes filesystems. Whether those filesystems share physical media depends on the deployment. SSH destinations still require the chosen computer's identity for the deposit. The source-side lock cannot prevent independent deletion or physical loss of the target after readback. A plain removal when no backup is configured remains supported and provides no recovery point.

## Headless owner operations

Run `BUN_BE_BUN=1 opencode /path/to/kuvo-link.js box backups <action>` on the owning installation, with the same data environment as its Box. A shell on that installation, including an authenticated OS login over SSH, acts with the owner's existing filesystem authority. Paired clients get only the health projection from `GET kuvo/box/backups/status`. Configuration and recovery require the local app or the owner command. Ordinary `box route` does not grant owner authority.

- `status` prints health. `report` prints local configuration details and the durable restore report.
- `destination` reads JSON on stdin. Supply `destination` and optionally `projects`, a list of absolute folder paths, for a preview. Set `confirm: true` to enable the selected destination. The key stays in the source's private `backup/configuration.json` with mode 0600. Retain the key in a private recovery location before losing the source. The command, receiver and paired status do not print it.
- `now` takes or returns today's verified point. `points` lists points using either the current destination or supplied `destination` and `source`. `match` establishes the accepted replacement mapping where required. `restore` reads `destination`, `source`, `id`, `recoveryKey` and `confirm: true` from stdin. Stop the data writers before restoring. Keep recovery keys out of command-line arguments and logs.
- `destination` with `enabled: false` stops new scheduled backups while keeping existing deposits. `erase` with a point `id` and `confirm: true` explicitly deletes an authorized point. Existing Relay tombstones reject delayed uploads for erased points. Retention runs when an enabled owner takes backups. Relay retention and erase require valid namespace authority, including the accepted replacement when using its matched namespace. The separate vault export and import still require the vault holder and use a distinct key.

Relay backup receivers hold ciphertext, not the recovery key. A replacement can read or erase
only its accepted source namespace and starts uploads under its own key; it cannot resume an old
owner’s reservation. The source reports a verified point only after reading back and authenticating
the archive. A retry can confirm a published point by checksum, and erase retires matching staging
so a delayed commit cannot recreate it. Ordinary unlink and wipe leave external deposits intact.

## Recovery evidence

New points record the source's managed attachment roots inside the encrypted archive. On restore, structured file references and attachment notes in backed-up transcripts resolve to the replacement's verified payloads. An occupied path keeps its current contents. The recovered attachment takes a distinct managed address. A known missing attachment points to an unavailable location so an unrelated file at the old address cannot satisfy it. The durable report itemizes named missing attachments, older Work Queue omissions, artifact versions without copies, and held conflicts. The archive records work present at its timestamp. It cannot enumerate work created afterward that did not reach another system.

Managed artifact history can open retained content-addressed copies without the original project path. A pruned version stays in history with its bytes unavailable. A file at the expected copy address must pass the size and digest checks before opening. An occupied artifact log or populated engine database is held for review under the existing conflict policy. Old archives without attachment-root metadata can recover bytes at their declared addresses. Their historical absolute references may still need manual recovery. This pass does not rebuild original external project paths, agent-native stores outside declared storage, or vault grants.

External-folder previews show each selected path and a bounded, advisory Git inventory of staged, dirty and untracked names. A folder can have an unavailable or truncated Git preview. Export walks the selected folder separately, including files ignored by Git. It records unsafe links and unsupported entries as itemized omissions. External folders restore under the recovery directory for deliberate placement.
