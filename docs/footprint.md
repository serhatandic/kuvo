# What Kuvo Code leaves on people's computers

CLAUDE.md's strict rule, "Footprint contained", points here for the details.

Kuvo Code must never spread files across the user's Mac or their machines. Everything it needs is packaged, kept in its own folders, organized inside them, and gone when those folders are deleted.

- **On the Mac**, only Kuvo Code's own places: `~/.kuvo-code` (active box and desktop data), `~/Library/Application Support/run.kuvo.code` (0.7 import and compatibility), `~/Library/Caches/run.kuvo.code`, `~/Library/Logs/Kuvo Code`, its `WebKit` and `HTTPStorages` folders, its preferences and its keychain items. Temporary files go in the app's temporary folder and are deleted once used. SSH connection sockets stay under the account’s home, in the box’s `run/ssh` or the desktop app’s `~/.kuvo-ssh-ctl`. When a path is too long for SSH connection reuse, the client opens a new connection for each request. The box keeps its SSH agent sockets under `run`, with `~/.kuvo-ssh` as a short path on macOS. If the complete socket name still exceeds the macOS limit, the box uses an owner-only directory under `/private/tmp/kuvo-ssh-<uid>`. SSH setup holds a reservation in `~/.kuvo-code-adding` while it changes the account. Trusted host keys go in `~/.kuvo-code/ssh/known_hosts`, add attempts in `run/adding.json`, and engine packages in `cache/engine-packs`. The box's installer (`kuvo-install`, #713), run from the release an app carries, writes only in `~/.kuvo-code/updates/install` (the release unpacked, the engine it fetched), which goes once a box is made from it; beside a box that's already there, the fetched engine goes once that box has the same one, and only the unpacked release (a few megabytes, one at a time) stays. Every box keeps the newest signed release it holds, whole, in `~/.kuvo-code/updates/release` (one, a few megabytes, replaced by the next), to hand to your other computers and to repair its own files from, and the one it runs apart in `updates/running` once a newer one is held there, or where it had none (fetched from the release feed or another of your computers; gone once it runs another; a repair writes each file it puts back beside it as `<file>.repair-<pid>`, renamed in place at once; each look noted in `run/repair.json`; it removes `bin/.own`, what an older Kuvo kept apart, once its files are found sound); one being pulled from another of your computers is gathered in `updates/incoming`, which goes once it's offered, refused, or the link starts again. The desktop app keeps its own files (the list of your computers, your settings on that device in `settings.json`, with whether the first Quit's note was seen, a log of its connections to your other computers in `link.log` (with the one before it, `link.log.1`, a megabyte at most); on Linux its device key too) in `~/.kuvo-code/desktop`, never in `~/Library/Application Support/run.kuvo.code`, which is Kuvo Code 0.7's folder: the move from 0.7 only reads it. The keeper’s runtime files and locks live inside the box. The login agent runs in the account’s launchd domain and Linux startup uses the account’s crontab. Kuvo leaves shell profiles, `/usr/local` and other apps’ folders alone.
- **On a remote machine**, everything goes in `~/.kuvo-code`: the engine, its XDG data, the agents bridge, browser, helpers, run state and trash. Never install system packages or ask for `sudo`, never write dotfiles or caches in the user's home, `/tmp` leftovers, crontabs or services. The one exception is a single `@reboot` line in the user's crontab, tagged `# kuvo-code`, that starts the engine again after the machine restarts, and on a Mac its login agent `~/Library/LaunchAgents/run.kuvo.code.machine.plist` beside it (only for the real `~/.kuvo-code`, never a test's); **Unlink** removes setup access and retains local work. **Unlink + wipe** revokes access, then removes Kuvo and its startup entries after any required backup and transfers verify. The site’s `uninstall.md` covers teardown. Bring dependencies along instead (the browser brings its own libraries and fonts). On a Mac, Chrome gets `CFFIXED_USER_HOME` as well; macOS still records its last run in the real `~/Library/Preferences/com.google.chrome.for.testing.plist`, which nothing we set stops, so **Uninstall from <machine>…** takes that key out. Anything Kuvo Code starts there runs with its folders pointed inside `~/.kuvo-code` (the engine's `XDG_*` folders; the browser gets a home of its own in `~/.kuvo-code/browser/home`) and starts from a folder inside it, so nothing relative lands elsewhere. Check after a change: list what's new in the machine's home folder and `/tmp`.
- **Except the coding agents' own programs** (Claude Code, Codex, Grok, Antigravity's `agy`), on the Mac and on machines (the user, 2026-10-23: "break the containment on machines for this"). Kuvo Code uses the ones on the computer's PATH (a machine's login shell's), and **Install** and **Update** run their makers' official installers and updaters (`curl -fsSL https://claude.ai/install.sh | bash`, `https://chatgpt.com/codex/install.sh`, `https://x.ai/cli/install.sh`, `https://antigravity.google/cli/install.sh`; `claude update`, `codex update`, `grok update`, `agy update`, or the Homebrew or npm that owns an install), with the machine's own folders, so they put them where they always do (`~/.local/bin`, `~/.local/share/claude`, `~/.codex`, `~/.grok`; `agy` in `~/.local/bin` with its download staged in `~/.cache/antigravity`; Grok's installer adds a PATH block to the shell profile). Kuvo Code never installs copies of its own of them, and only when you click Install or Update. Their sign-ins are theirs too: the first account is the agent's own sign-in in its own folder (`~/.claude`, `~/.codex`, `~/.grok`), on a Mac and a machine alike, shared with Terminal (the user, 2026-11-22); accounts you add are in `~/.kuvo-code/agents/<agent>/accounts`. Antigravity's sign-ins stay in Kuvo Code's folders (`~/.kuvo-code/agents/antigravity/profile`, its own GEMINI_HOME, never `~/.gemini`), and so does Google's earlier Antigravity agent (1.3.0) where an account signed in before `agy` still runs on it. Cursor's SDK still comes with Kuvo Code, in its folders.
- **Except the git repositories its sandbox keeps on Linux** (#429). Each command's namespace keeps git's own files read-only there, which only works for names that already exist. So in each repository a conversation's commands write on Linux (its own, Also Allowed ones, their submodules' repositories), the launcher adds what a repository lacks of them, never changing one that's there: `.git/commondir` holding `./`, and empty `.git/hooks`, `.git/modules`, `.git/worktrees` and `.git/config.worktree`; in each linked worktree's own folder (`.git/worktrees/<name>`), an empty `config.worktree` and `modules`. git and libgit2 read them as having none, but for what `git rev-parse --git-common-dir` and `--git-path` print (absolute paths). They stay after uninstalling, harmless; `uninstall.md` says how to take them out (only `commondir` if it holds `./`, and only empty folders and files).
- **Except git's own watcher, where your settings turn it on** (#341). On a Mac, the box's git keeps `core.fsmonitor = true` as your settings give it (never a program they name), so git starts its own `git fsmonitor--daemon` for each repository or worktree it reads, as your terminal's git would, and it runs on after Kuvo Code quits until git stops it. Nothing of Kuvo Code's is left: the daemon and its socket in the repository's `.git` are git's, and only where you asked for them.
- **Backup deposits and wipe receipts**. Encrypted deposits on another computer use its
  `~/.kuvo-backups` directory. Relay archives live under its `relay` subdirectory. Ordinary
  unlink and Kuvo data wipe preserve these separate archives. The installer keeps the last
  wipe receipt beside the erased Box or App Support root and clears it after reinstall.
- **Organized inside**: a folder per kind (`engine/<version>`, `browser/<build>`, `bin`, `run`, `keys`, `bots`, `groups`, `trash`), the active `bin` symlink selecting `versions/<version>-<sha12>/bin`, and
  `run/previous` recording the rollback target. A staged release can sit beside
  the running release. Older installations may still have a real `bin` directory.
  A staged Rust release keeps its signed manifest and archive in its version's
  folder beside `bin`. The running computer can send that archive to one of
  your other computers through the relay, including after the feed drops it.
  The active box also keeps its engine data under the keeper's `XDG_DATA_HOME`,
  with bridge and group stores in the box home.
- **Removing the folders removes everything**: `uninstall.md` and `privacy.md` list them all; anything new keeps that true and updates them. After a change, list what's new in the computer's home folder and `/tmp`.
- **Tests and demo copies too**: they use folders of their own (`KUVO_DEMO_MACHINE_ROOT`, `~/.kuvo-code-test`), keep test files inside them, and clean up what they leave on a machine or the Mac when done. A home folder of a test's own doesn't keep a script from `crontab` or `launchctl`, which are the account's: stand-ins come first on its PATH, and a run that changes the real ones fails.
